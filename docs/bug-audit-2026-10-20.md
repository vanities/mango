## Background transfer lifecycle

Both transfer managers now distinguish system expiration from explicit Cancel. Expiration
stops the current worker between chunks, preserves its partial file and the pending queue,
and completes that execution unsuccessfully once. A later background execution or foreground
activation resumes pending work. Explicit cancellation is persisted before the worker stops;
queue restoration preserves it, and Earmark no longer restarts cancelled jobs automatically.
Foreground activation ends the previous background execution immediately, so a delayed expiry
from that execution cannot pause foreground transfers. Callback identities also reject expiry
from an older execution after a new execution starts.

`TransferBackgroundExecution` adapts the real BGProcessingTask callback/completion boundary.
Tests inject that boundary into the actual manager; they do not fabricate a BGProcessingTask
or prove when iOS will grant processing time. Test-only configuration disables both background
registration and scheduling. Old queue JSON without the optional cancellation intent still decodes.

## Replaced sources during partial-download retry — 2026-10-21

Cancelling an actual SMB download, replacing the generated remote CBZ with a different
equal-sized valid CBZ, and retrying produced a completed download containing both versions.
The same pattern reproduced with Earmark WAV audio. Growing replacements also require
refreshing the queue's cached byte count.

Both managers now record the source endpoint, path, current size, modification time and
first/last 64 KiB SHA-256 samples beside an app-owned partial. Legacy, corrupt, oversized,
changed or undated partials restart. Before resuming an otherwise matching partial, every
retained byte is compared with the live source through bounded reads. This last check is
necessary: an Earmark fixture changed only in its retained middle, preserving its size,
timestamp and sampled bytes, still failed the snapshot-only implementation. Verified bytes
remain on disk, but Retry must reread the retained prefix because the SMB API exposes no
immutable version identifier. Cancellation is honored during verification.

The completed length and source snapshot are checked again before promotion; a detected
change during transfer remains partial and reports an error. Successful promotion removes
the sidecar. These checks do not provide an atomic snapshot of a concurrently edited NAS
file, particularly a writer preserving metadata and changing only unsampled bytes during
the transfer. Existing already-completed destination shortcuts are outside this partial-resume fix.

## WebContent process recovery

A simulator probe now terminates the actual WebKit child process while a generated EPUB is
open. The final helper reads the owned web view's process identifier, validates it is live
and is neither PID 0/1 nor the test host, and sends SIGKILL only to that simulator child.
The private identifier getter is confined to test bundles; production uses the public
navigation delegate. The getter is documented in
[WebKit's own header](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewPrivate.h).
Unsupported simulator runtimes fail clearly; physical-device runs explicitly skip these probes.

This caught a regression in the **unshipped** current-navigation filter added during this
audit. WebKit automatically reloaded a terminated page with a fresh navigation token. The
filter rejected that completion, leaving raw chapter text without its styles or pager.
Both red runs killed a real child process and failed to recover. Targeted start/finish logs
confirmed the new token was rejected, and JavaScript confirmed chapter text existed with
`window.mangoPager` absent. The correction owns the recovery navigation explicitly, resets
chapter/style readiness, and keeps the last reported reading position. Retired and closed
readers cannot initiate recovery.

Scrolling additionally did not retain its recovery offset. Tracking that offset alone was
insufficient: WebKit resets the native scroll view before its termination callback, producing
a false zero. Empty-layout offsets are ignored, and scroll reports are deferred one main-queue
turn and checked against the active navigation. Reports are suppressed while the saved scroll
offset is being restored, and delayed restores also verify their navigation token.
Release stress testing additionally caught native content height arriving after the old
250 ms restore callback. Restoration now remains pending, with progress suppressed, until
a positive scrollable range arrives. Its content-size observation is cancelled on navigation,
termination and dismantling, and still checks the current navigation before restoring.

`testScrollingChapterWaitsForDelayedLayoutAfterProcessTermination` hides generated chapter
content for 800 ms to reproduce delayed layout. With the pre-fix implementation and verified
process termination, it failed at offset 0 rather than 55%, with the old process gone, a new
navigation and fresh document context. `/tmp/mango-release-verified-layout-red-20261021.xcresult`
retains that failure. `/tmp/mango-release-signal-recovery-stress-20261021.xcresult` passes 20
normal/delayed recovery repetitions with the fix. Temporary tagged tracing was removed.

The earlier private `_killWebContentProcess` request sometimes left the old OS process alive
and the original JavaScript marker intact while its private PID getter returned zero.
Those repetitions were invalid fault injection, not failed reader recovery. The final shared
test helper uses verified OS termination; recovery also checks old-process exit, fresh
navigation/document state, exact restored position and absence of false progress reports.

The permanent tests exercise actual rendered EPUBs and real process replacement:

- Paged recovery retains a nonzero fraction without turning chapters.
- Scrolling recovery retains 55 percent and never reports a false position of zero.
- The full `NovelReaderView` advances from Chapter 1 to Chapter 2, turns a page, survives three
  consecutive process terminations, and checks saved chapter/fraction plus the widget snapshot
  after each recovery. The restored pager also accepts another real keyboard page turn.
- Existing stale-failure coverage now verifies that retired/closed readers cannot reload.

## Reader lifetime on iOS 27

The full `NovelReaderView` + `NovelEngine` SMB integration passed 39 rapid chapter transitions,
background-notification saves with matching widget snapshots, manual client reconnects,
and three book completions on the iOS 27.0 iPhone 17 Pro simulator:
`/tmp/mango-ios27-reader-engine-stress-20261020.xcresult`.

A separate close-and-release probe reproduced a reference cycle:
`NovelEngine.onReachedEnd` captured the reader View's State, which owned the engine again.

Two chapter-transition faults were reproduced and fixed:

- `EPUBSchemeHandler` checked whether a request was stopped only before delivering its response.
  If delivery reentrantly stopped the request, it still delivered data and/or completion.
  Apple's local SDK `WKURLSchemeTask.h` explicitly documents an exception for callbacks after stop.
  Regression tests stop requests during response and data callbacks: both failed before the fix
  and now pass. Liveness is checked between each delivery callback, without holding a lock across
  calls into WebKit.
- A queued burst of 20 boundary events from one old chapter produced 20 chapter changes before
  SwiftUI replaced its web view. A delivery-time check now compares the reader engine's current
  chapter index and bookmark/jump identity, and rejects messages after the book reaches its end.
  The coordinator also rejects messages from a different document, ignores callbacks before the
  chapter loads, and explicitly detaches handlers/delegates and stops loading during teardown.
  The regression alternates clicks and keyboard turns, sends stale progress after each turn,
  asserts exactly one chapter change, and verifies retired web views are released.
